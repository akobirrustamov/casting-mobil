## 1. Этап A — аккаунт разработчика [ЗАКАЗЧИК]

Самый длинный по календарю этап: не из-за работы, а из-за проверок на стороне
Google. Начинать надо первым, всё остальное делается параллельно.

### 1.1. Регистрация

1. Открыть **https://play.google.com/console/signup**
2. Войти под Google-аккаунтом заказчика.
   ⚠️ **Не личная почта сотрудника, а рабочий ящик компании.** Владельца
   аккаунта не переименовать на другого человека, а сотрудник может уволиться.
3. На шаге «Select account type» выбрать **Organization** (не «Yourself»).
   ⚠️ **Выбор делается один раз и не меняется.** Личный аккаунт потребовал бы
   закрытого тестирования: минимум 12 тестировщиков, непрерывно 14 дней, и
   только потом заявка в продакшен. Организации от этого освобождены — ровно
   поэтому мы берём Organization.
4. Оплатить регистрационный взнос **$25** (разово, не ежегодно).
   ⚠️ Карта нужна международная — Visa/Mastercard с разрешёнными зарубежными
   платежами. UzCard/Humo не подойдут.

### 1.2. Верификация организации

Google запросит (для Узбекистана — по официальной справке Google):

- **регистрационный документ компании** — одно из: свидетельство о регистрации,
  выписка из реестра, лицензия, налоговый сертификат;
- **удостоверение личности представителя** — паспорт, ID-карта, водительское
  удостоверение или вид на жительство;
- **D-U-N-S номер** организации.

⚠️ **D-U-N-S заказывать в первый же день.** Он бесплатный, но выдаётся до
30 дней. Заявка: **https://www.dnb.com/duns/get-a-duns.html** → «Get a D-U-N-S
Number». Название и адрес компании в заявке должны **совпадать посимвольно** с
тем, что будет вписано в Play Console, иначе Google не сматчит данные и вернёт
на доработку.

Статус проверки: **https://play.google.com/console** → слева внизу
**Settings → Developer account → Account details**.

### 1.3. Выдать доступ вам и мне [ЗАКАЗЧИК]

1. https://play.google.com/console → слева внизу **Users and permissions**
2. Кнопка **Invite new users** (справа вверху)
3. Email → в блоке **App permissions** выбрать приложение (появится после §4)
   и отметить:
   - `View app information and download bulk reports`
   - `Manage store presence`
   - `Manage testing tracks`, `Release to testing tracks`
   - **`Release to production` — только вам**
4. **Invite user**

⚠️ Роль `Admin (all permissions)` не выдавать никому, кроме владельца: с ней
можно удалить приложение целиком.

## 2. Этап B — что я уже сделал в проекте [Я]

### 2.1. Урезал разрешения

Было (Expo добавлял по умолчанию):

```
android.permission.READ_EXTERNAL_STORAGE
android.permission.WRITE_EXTERNAL_STORAGE
android.permission.INTERNET
```

Стало — только `INTERNET`. В `app.json` добавлено:

```json
"blockedPermissions": [
  "android.permission.READ_EXTERNAL_STORAGE",
  "android.permission.WRITE_EXTERNAL_STORAGE"
]
```

Зачем: приложение не читает и не пишет файлы пользователя — ни камеры, ни
выбора файлов в коде нет. Лишнее разрешение в манифесте — это лишний вопрос на
ревью и расхождение с формой Data safety, где мы честно отвечаем «файлы не
собираем».

Проверка:

```bash
cd mobile
npx expo config --type prebuild --json | grep -o '"permissions":\[[^]]*\]'
# → ["android.permission.INTERNET"]
```

⚠️ Это нативная правка: она приезжает **только новой сборкой**, не через
`eas update`.

### 2.2. Настроил профиль отправки в Play

В `eas.json` появился блок:

```json
"submit": {
  "production": {
    "android": {
      "serviceAccountKeyPath": "./play-service-account.json",
      "track": "internal",
      "releaseStatus": "draft",
      "changesNotSentForReview": false
    }
  }
}
```

Это позволит грузить сборку командой `eas submit` вместо ручной загрузки файла.
Ключ `play-service-account.json` вы получите в §3; он добавлен в `.gitignore` —
**в репозиторий он не должен попасть никогда**, это доступ к релизам.

## 3. Этап C — сервисный аккаунт для загрузки сборок [ВЫ]

Делается один раз. Без него каждую сборку придётся скачивать и загружать руками.

1. **Play Console → Setup → API access**:
   https://play.google.com/console → слева **Setup** → **API access**
2. **Choose a project to link** → **Create new project**. Либо привязать
   существующий проект `497193534365`, в котором уже живёт Google-вход — тогда
   всё в одном месте.
3. Блок **Service accounts** → **Create new service account**. Появится
   подсказка со ссылкой в Google Cloud — перейти по ней:
   https://console.cloud.google.com/iam-admin/serviceaccounts
4. **Create service account**:
   - Service account name: `play-publisher`
   - **Create and continue** → роль в Google Cloud можно не давать (права
     выдаются в Play Console) → **Done**
5. В списке нажать на созданный аккаунт → вкладка **Keys** → **Add key** →
   **Create new key** → тип **JSON** → **Create**. Файл скачается сам.
6. Переименовать файл в `play-service-account.json` и положить в папку
   `mobile/` рядом с `eas.json`.
   ⚠️ Не коммитить. Он уже в `.gitignore`, но перед коммитом гляньте
   `git status`.
7. Вернуться в **Play Console → Setup → API access** → **Refresh service
   accounts** → у нового аккаунта **Manage Play Console permissions** →
   отметить `Release to testing tracks`, `Release apps to production`,
   `Manage store presence` → **Invite user**.

Проверка (запускаю я, когда будет первая сборка):

```bash
cd mobile
export EXPO_TOKEN=$(grep '^EXPO_TOKEN=' .env.local | cut -d= -f2)
eas submit -p android --profile production --latest
```

### 5.4. ⚠️ Демо-доступ: без него ревью встанет [БЭК]

Вход в приложении — по SMS-коду на узбекский номер. Ревьюер Google сидит в
другой стране и SMS не получит. Нужен **фиксированный тестовый номер на
проде**, для которого сервер принимает заранее известный код (например
`+998 90 000 00 00` → `0000`) и не отправляет настоящую SMS.

### ✅ Сделано 13.09.2026 — но на проде выключено

Механизм в `OtpService`: для одного номера SMS не отправляется, а код
фиксированный. **По умолчанию выключен** — работает только если заданы обе
настройки:

```properties
app.otp.demo.phone=+998900000000
app.otp.demo.code=0000
```

⚠️ **Код ровно 4 цифры** — поле ввода в приложении четырёхзначное, шести
цифр там просто не набрать. Тест это фиксирует.

⚠️ **Демо-аккаунту выдаётся Premium** (`app.otp.demo.premium-days`, по
умолчанию 90 дней): часть каталога закрыта подпиской, и без неё ревьюер не
увидел бы половину приложения, а заодно упёрся бы в неработающую кнопку
оплаты. Выдаётся только этому номеру и только когда срок подходит к концу.

⚠️ Номер и код выбрать свои, эти — пример. Включить перед отправкой на
ревью, **после проверки выключить**. При включении в лог пишется `WARN` —
чтобы настройка не осталась на проде незамеченной.

Тесты (`DemoPhoneOtpTest`) отдельно проверяют главное: демо-код **не
работает на других номерах**.

Что именно нужно от бэкенда —
[roadmap/PLAY_BACKEND_TASKS.md](../../roadmap/PLAY_BACKEND_TASKS.md) §3.

Запасной вариант, если бэкенд не успеет: написать в инструкции, что вход
выполняется кнопкой **Sign in with Google** любым аккаунтом. Тогда §7
(публикация OAuth-проекта) становится **строго обязательной до отправки** —
иначе Google-аккаунт ревьюера получит «доступ запрещён», и со стороны это
выглядит как сломанное приложение.

## 6. ⚠️ Блокер: удаление аккаунта [БЭК] + [Я]

Политика Google: если в приложении можно **создать аккаунт**, должно быть и
удаление — **двумя путями**:

1. **внутри приложения** — путь в интерфейсе, не длиннее пары экранов;
2. **по веб-ссылке** — доступной без установки приложения; её вписывают в
   App content → **Data deletion**.

Сейчас нет ни того, ни другого: в `app/settings/profile.tsx` удаления аккаунта
не существует.

## 6a. ⚠️ Блокер: комментарии = пользовательский контент [БЭК] + [Я]

Появилось 10.09.2026 вместе с разделом комментариев
(`src/features/comments/`). Для Google это **UGC — user-generated content**, и
к таким приложениям применяется отдельная политика.

Что политика требует от приложения — и что у нас есть:

| Требование | Есть | Комментарий |
|---|---|---|
| Модерация контента | ✅ | модератор скрывает комментарий, автору он виден как «скрыт» |
| Блокировка нарушителей | ✅ на стороне админки | заблокированный получает `403` при отправке |
| Удаление своего контента | ✅ | мягкое удаление, для модерации запись остаётся |
| **Кнопка «Пожаловаться» на чужой комментарий** | ❌ | в интерфейсе её нет |
| **Возможность заблокировать автора для себя** | ❌ | в интерфейсе её нет |

Последние два пункта Google проверяет прямым сценарием: открывает список
комментариев и ищет способ пожаловаться. Не находит — отказ со ссылкой на
User Generated Content policy.

### ✅ Сделано на бэкенде 13.09.2026

`POST /api/v1/app/comments/{id}/report` с причиной (`SPAM`, `INSULT`,
`ADULT`, `OTHER`), таблица `cms_comment_report`, тесты `CommentReportTest`.

Правила: один человек — одна жалоба на комментарий (`409`), на свой
комментарий пожаловаться нельзя (`422`), удалённый комментарий — `404`.
Жалоба **не скрывает** комментарий: решение принимает модератор.

⚠️ В админке ничего дорабатывать не пришлось: фильтр «только с жалобами» и
сортировка по числу жалоб там были с самого начала — просто счётчик
`reports_count` никто не увеличивал, и фильтр всегда возвращал пустоту.

### ✅ Кнопка в приложении готова 13.09.2026

У чужого комментария — флажок «Пожаловаться», у своего — корзина;
вместе они не появляются. По нажатию открывается шторка с четырьмя
причинами. Тесты: `report.test.tsx`.

⚠️ **Не системный диалог, а шторка** — в `Alert` на Android помещается
максимум три кнопки, а причин четыре плюс отмена: два варианта просто не
отрисовались бы.

⚠️ Ответ показывается всегда, в том числе при отказе: жалоба ничего не
меняет на экране, и молчание неотличимо от «кнопка не работает».

Осталось:

| Кто | Что |
|---|---|
| **[БЭК]** | решить по «скрыть автора» (мьют): делаем или письменно фиксируем, что жалобы достаточно |

Контракт эндпоинта жалобы и список причин —
[roadmap/PLAY_BACKEND_TASKS.md](../../roadmap/PLAY_BACKEND_TASKS.md) §2.

⚠️ Если по срокам не успеваем, есть законный обходной путь: **временно
отключить комментарии** (не показывать раздел) и выпустить первую версию без
них, а включить их обновлением, когда жалобы будут готовы. Это честнее, чем
пытаться проскочить ревью — снятое приложение возвращается в магазин дольше,
чем занимает сама доработка.

## 9. ⚠️ Блокер: SHA-1 ключа Play App Signing [ВЫ]

Самая частая и самая «тихая» поломка: приложение проходит ревью, публикуется —
и у всех ломается вход через Google.

Причина: Google подписывает то, что раздаёт из магазина, **своим** ключом
(Play App Signing), а не ключом EAS. Отпечаток становится другим, и
Android-клиент Google перестаёт узнавать приложение.

1. Загрузить первую сборку (§10) — раздел появляется только после неё.
2. **Play Console → Release → Setup → App integrity** → вкладка **App signing**
   → блок **App signing key certificate** → скопировать **SHA-1 certificate
   fingerprint**.
3. Открыть
   **https://console.cloud.google.com/auth/clients?project=uzcasting**
4. **+ Create client** → тип **Android**:
   - Name: `UzCasting Android (Play)`
   - Package name: `uz.uzcasting.app`
   - SHA-1: отпечаток из шага 2
   - **Create**

На 13.09.2026 в проекте уже три клиента, и это нормально:

| Имя | Тип | Зачем |
|---|---|---|
| `UzCasting` | Web application | `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, проверка токена на бэкенде |
| `UzCasting Android` | Android | `EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID`, ключ EAS |
| `UzCasting Android Diyorbek` | Android | клиент коллеги под его ключ разработки |

Четвёртый — под ключ Play — встанет рядом и ничего не перетрёт.

⚠️ **Именно новый клиент, а не правка старого.** В Android-клиенте поле SHA-1
одно, второй отпечаток туда не дописать — старый заменится, и сломается вход в
наших внутренних сборках. Клиентов с одинаковым package может быть несколько,
подходящий Google выберет сам по подписи.

⚠️ Изменения у Google применяются от 5 минут до нескольких часов. Проверять
вход надо на сборке, скачанной **из Play** (internal testing), а не на APK с
диска — подпись у них разная.

## 12. После публикации

### Что можно менять без новой сборки и без ревью

`eas update` доставляет JS-часть по воздуху: экраны, тексты, переводы, логику
запросов, картинки из `assets/`. Ревью Google для этого не нужно.

```bash
eas update --channel production --environment production --message "что поменялось"
```

⚠️ `eas update` **не читает** `env` из `eas.json` — переменные берутся из
окружений EAS. Разбор с последствиями — [BUILDS_AND_UPDATES.md](./BUILDS_AND_UPDATES.md) §2.

### Что требует новой сборки и нового ревью

Нативные изменения: новые библиотеки, правки `app.json` (иконка, разрешения,
схемы), смена версии Expo SDK. Изменения карточки магазина Google тоже
проверяет, но быстрее.

## 13. Частые причины отказа — и как мы их закрываем

| Причина | У нас |
|---|---|
| Политика конфиденциальности не открывается / не та | ✅ `/maxfiylik`, 200, тот же домен |
| Нет удаления аккаунта | ✅ §6 — эндпоинт, страница и экран готовы |
| Пользовательский контент без жалоб | ✅ §6a — жалоба на комментарий готова |
| Ревьюер не смог войти | ✅ §5.4 — демо-номер с Premium (включить на проде) |
| Не заявлена реклама | ✅ заявляем «Yes» (§5.2) |
| Data safety расходится с поведением приложения | ✅ ответы сверены с кодом (§5.7) |
| Оплата цифрового контента мимо Google Play Billing | ✅ платежей в сборке нет |
| Пустые или обрезанные скриншоты | ⏳ §8.3 |
| Target API ниже требуемого | ✅ API 36 |
| Разрешения, которыми приложение не пользуется | ✅ остался только `INTERNET` |

⚠️ **Про платежи отдельно.** Как только в приложении появится реальная покупка
подписки, серий или Stars — Google требует проводить её **через Google Play
Billing** с комиссией. Внешняя оплата (Payme/Click/Uzum) внутри приложения за
цифровой контент запрещена и ведёт к снятию. Это продуктовое решение, и
принимать его надо **до** того, как писать код оплаты.
