# API — что уже есть

> Разбор боевого бэкенда по коду сайта (`frontend/src`) и живым запросам.
> База: `https://uzcasting.com` — боевой домен приложения (TLS с 30.08.2026;
> на `http://` nginx отвечает `301`, а это ломает POST — см. LOCAL_BACKEND.md §9).
> Раньше был `https://uzcasting.site`; старый кастинговый модуль отвечает на
> обоих. Адрес задаётся через `EXPO_PUBLIC_API_URL`, разбор — в
> [LOCAL_BACKEND.md §9](./LOCAL_BACKEND.md).
> В мобильном приложении — `EXPO_PUBLIC_API_URL`, по умолчанию прод.

Последнее обновление: 22.08.2026

---

## 1. Главное

Бэкендов, по сути, **два, и они живут в одном приложении**:

| Namespace | Что это | Где работает |
|---|---|---|
| `/api/v1/**` (кроме `/app`) | старый кастинговый модуль: анкеты, файлы, новости, вход | боевой `uzcasting.site` |
| `/api/v1/app/**` | новая платформа: главная, контент, entitlement, медиа | **только локально** |

⚠️ **На проде пока старая сборка.** `GET /api/v1/app/home` там отвечает `200`, но
телом отдаёт `index.html` сайта — SPA перехватывает неизвестный путь. Это не 404,
поэтому axios ошибкой такой ответ не считает: клиент обязан сам проверять форму
ответа (см. `HomeFeedUnavailableError` в `src/features/home/api.ts`).

Чтобы работать с новой платформой, поднимайте бэкенд локально — [LOCAL_BACKEND.md](./LOCAL_BACKEND.md).

**Кастинговая часть уже работает.** Это не проект с нуля: есть Spring-бэкенд, сайт на нём, Telegram-бот и админка. Мобильному приложению не нужно ждать контракта, чтобы показать каталог креаторов — эндпоинт живой и отдаёт реальные данные.

Проверено запросом: `GET /api/v1/casting-user/web` → `200`, ~68 КБ, реальные анкеты.

Каталог креаторов на главной уже подключён к нему по-настоящему (`src/features/creators`). Премьеры и кастинг-объявления — на временных данных, для них эндпоинтов нет.

## 2. Известные эндпоинты

Собраны из кода сайта. Схемы запросов/ответов документированы только там, где мы их реально используем.

### Публичные

|---|---|---|
| `GET` | `/api/v1/casting-user/web` | каталог анкет с `isWebShow = true` |

Авторизация — заголовок `Authorization` с токеном (на сайте лежит в `localStorage.access_token`). В мобильном будем хранить в `expo-secure-store`.

### Телефон и SMS-код (Eskiz)

⚠️ **OTP переехал в `/api/v1/app/**` (28.08.2026).**

Сначала эти эндпоинты появились в `/api/v1/auth/**` — то есть в
ЗАМОРОЖЕННОМ пространстве старого кастингового модуля, которым
пользуются Telegram-бот и старая админка. Любое изменение там задевает
их, поэтому новая функциональность туда не добавляется.

Тест `OldCastingFrozenTest` это и поймал.

⚠️ **Пароль отменён целиком (04.09.2026).** Заказчик убрал и разделы
«Kirish / Ro'yxatdan o'tish», и сам пароль: номер всё равно
подтверждался по SMS, то есть пароль был не вторым замком, а вторым
шагом, который забывают, — и «забыли пароль» так и не написали.

Эндпоинты `register/start`, `register/confirm`, `register/complete` и
`/app/auth/login` **удалены** с бэкенда. Пространство `/api/v1/app/**`
принадлежит только мобильному приложению, других клиентов у них не было.
Пароль админ-панели живёт отдельно — `/api/v1/app/admin/auth/login`.

Вход и регистрация — один поток. «Ты новый или старый» не спрашивается:
на это отвечает сервер, и только после кода.

```jsonc
// Шаг 1. Занятый номер — НЕ ошибка: это просто входящий человек.
POST /api/v1/app/auth/otp/send      { "phone": "+998901234567" }
→ { "sent": true, "expiresInSeconds": 180 }

// Шаг 2. Два разных ответа.
POST /api/v1/app/auth/otp/verify    { "phone": "+998901234567", "code": "1234" }

// (а) аккаунт есть и у него есть имя — сессия выдаётся прямо здесь:
→ { "name_required": false,
    "access_token": "...", "refresh_token": "...",
    "roles": [{ "name": "ROLE_USER" }],
    "user": { "id": "...", "name": "Aziz Karimov", "phone": "998901234567" } }

// (б) аккаунта нет (или он без имени) — токена НЕТ, номер помечен
//     подтверждённым на 15 минут:
→ { "name_required": true, "expiresInSeconds": 900 }

// Шаг 3 — только после (б). Здесь создаётся аккаунт и сразу выдаётся сессия.
// `name` обязателен (2–60 символов): без него аккаунт оставался безымянным
// в профиле и под комментариями.
POST /api/v1/app/auth/otp/complete  { "phone": "+998901234567", "name": "Aziz Karimov" }
→ { "name_required": false, "access_token": "...", "refresh_token": "...",
    "roles": [...], "user": {...} }
→ 422 { "code": "PHONE_NOT_VERIFIED" }   // метка просрочена или уже использована
```

Экраны: `app/(auth)/sign-in.tsx` (номер) → `app/(auth)/otp.tsx` (код) →
либо сразу `/(tabs)`, либо `app/(auth)/name.tsx` (имя) → `/(tabs)`.

**⚠️ Развилку решает `name_required`, а не наличие токена.** Флаг сказан
прямо, пустое поле выглядело бы случайностью. Разбор — в `verifyOtp()`,
экран получает уже размеченный результат.

**⚠️ Почему аккаунт создаётся на третьем шаге, а не на втором.** Иначе
человек, закрывший приложение на экране имени, оставался бы в базе
безымянной строкой. Аккаунт рождается вместе с именем; метка
«номер подтверждён» живёт 15 минут (`app.otp.verified-ttl-seconds`) и
одноразовая — `consumeVerified` гасит её при создании.

**⚠️ Аккаунты без имени.** Такие строки в базе есть: их оставляли старый
`otp/verify` (find-or-create без имени) и вход через Google. Они
проходят по ветке (б) и чинятся сами — человек один раз называет имя
СВОЕМУ ЖЕ аккаунту: id, покупки и избранное сохраняются.

**⚠️ Колонка `users.password_set` (миграция V30) осталась, но её больше
никто не читает.** Столбец не удалён намеренно: миграция ради мёртвого
поля рискованнее, чем само поле.

- Код 4-значный, живёт 3 минуты, хранится хешем (BCrypt) в памяти сервера.
- Повторная отправка — не раньше чем через **2 минуты**, иначе `429 OTP_COOLDOWN`.
  Экран `otp.tsx` держит свой отсчёт, чтобы не жать зря.
- 5 неверных попыток закрывают код: `429 OTP_LOCKED`, нужен новый.
- Телефон нормализуется к `998XXXXXXXXX`, формат ввода клиента значения не имеет.
- Лимит по IP: `otp/send` — 5/мин, `otp/verify` и `otp/complete` — 15/мин
  (`RateLimitFilter`).

Ошибки приходят обычным `ApiError { code, message }` (ТЗ §94). Текст оттуда —
только на узбекском, поэтому приложение переводит по `code`
(`src/features/auth/authErrors.ts`): `OTP_COOLDOWN`, `OTP_INVALID`, `OTP_EXPIRED`,
`OTP_LOCKED`, `SMS_NOT_CONFIGURED`, `SMS_SEND_FAILED`, `PHONE_NOT_VERIFIED`,
`NAME_INVALID`.

**⚠️ Без `ESKIZ_EMAIL` / `ESKIZ_PASSWORD` в `application.properties` отправка
падает `503 SMS_NOT_CONFIGURED`** — намеренно, как и Google без ключей: молчаливый
«успех» без SMS был бы хуже. Текст сообщения задан шаблоном
`app.otp.message-template` и должен совпадать с одобренным в кабинете Eskiz,
иначе шлюз отклонит отправку.

## 3. `GET /api/v1/casting-user/web`

Отдаёт массив анкет. Фактические поля:

```jsonc
{
  "id": 5,
  "telegramId": "...",
  "castingType": "euromodel",
  "gender": "female",
  "name": "...",
  "region": "Andijon",
  "nationality": "Ozbek",
  "birthday": "2007-11-18T00:00:00",
  "age": 17,
  "height": 170,
  "hairColor": "Jigar rang",
  "eyeColor": "Jigar rang",
  "clothSize": "xs", "shoeSize": "37",
  "bust": "75", "waist": "55", "son": "83",
  "email": "...", "phone": "...", "telegram": "...",
  "facebook": "...", "instagram": "...",
  "price": 390.0,
  "createdAt": "...",
  "status": 1, "firstChan": 1, "secondChan": 0,
  "isWebShow": true,
  "photos": [{ "id": "uuid", "prefix": "/users/...", "name": "...", "isWebShow": false }]
}
```

### Правила, которые нужно повторять

- Показывать только фото с `isWebShow: true`. У многих анкет таких фото нет вовсе — их не выводим (`withPhotos()`).
- `age` присылается не всегда — считаем из `birthday` (то же самое делает сайт).
- `castingType` приходит в разном регистре — приводим к нижнему.

### ⚠️ Эндпоинт публичный и отдаёт персональные данные

Без авторизации возвращаются `phone`, `email`, `telegram`, `instagram`, точная дата рождения и замеры фигуры — в том числе несовершеннолетних (в выдаче есть анкета с `age: 17`). Сайт эти поля не показывает, но они уходят на клиент, и их видно в любом браузере или curl.

Мобильное приложение эти поля не тянет намеренно — в `Creator` их нет. Но проблема на стороне бэкенда, клиентом она не решается.

**Что предложить бэкендерам:** отдавать на публичном эндпоинте только витринные поля (`id`, `name`, `castingType`, `gender`, `region`, `age`, `height`, публичные фото), а контакты — отдельным авторизованным запросом. Заодно снимет и вес ответа: сейчас 68 КБ на список.

Решение за заказчиком, но озвучить это стоит — персональные данные несовершеннолетних в открытом доступе.

### ⚠️ Причина найдена: правила доступа отключены целиком

`backend/.../Security/SecurityConfig.java`:

```java
.requestMatchers(HttpMethod.GET,    "/**").permitAll()
.requestMatchers(HttpMethod.DELETE, "/**").permitAll()
.requestMatchers(HttpMethod.PUT,    "/**").permitAll()
.requestMatchers(HttpMethod.POST,   "/**").permitAll()
```

Разрешены **все методы на всех путях без токена** — включая `DELETE` и админские эндпоинты (`/api/v1/casting-user/status/...`, `/api/v1/casting-user/{id}`, `/api/v1/admin/statistic`). JWT-фильтр написан и работает, но эти правила его обесценивают: проверять нечего, потому что разрешено всё.

То есть дело не в одном «болтливом» эндпоинте — публичен весь API, на запись тоже.

Чинится сужением правил: `permitAll` оставить только действительно публичному (`/api/v1/auth/**`, `GET /api/v1/news`, `GET /api/v1/file/getFile/**`, витрина каталога), остальное — `.authenticated()` и проверка ролей. Работа по бэкенду, но знать нужно всем: пока так, защита на клиенте ничего не значит.

## 5. Новая платформа — `/api/v1/app/**`

Появилась 19–22.08.2026. Токен для чтения не нужен, но если он есть — учитывается.

### `GET /api/v1/app/home?locale=UZ|RU|EN`

Вся главная одним ответом (ТЗ §31). Состав рядов, их порядок и заголовки задаёт
админ-панель — **в клиенте главная не зашита**, добавить ряд можно без релиза в стор.

```jsonc
{
  "locale": "UZ",
  "showAds": true,            // false у тех, у кого активна подписка
  "sections": [
    { "id": 1, "type": "ADVERTISEMENT_CAROUSEL", "title": "Reklama", "sortOrder": 0,
      "banners": [...], "content": [], "categories": [], "creators": [] }
  ]
}
```

Из четырёх массивов в секции заполнен ровно один — по типу секции:

| Тип секции | Массив | Что внутри |
|---|---|---|
| `ADVERTISEMENT_CAROUSEL` | `banners` | реклама; коммерческая скрыта у подписчиков |
| `NEW_PREMIERES` | `banners` | промо-баннеры премьер |
| `CATEGORIES` | `categories` | разделы каталога контента. **Ряд плиток не рисуется** — заказчик 01.09.2026 попросил убрать; вместо него ряды с карточками из `/app/catalog` (см. ниже) |
| `POPULAR_CREATORS` | `creators` | креаторы контента |
| `MINI_SERIES` · `REELS_SERIES` · `PODCASTS` · `SHOWS` · `STREAMS` · `CLIPS` · `FEATURED_CONTENT` · `POPULAR_CONTENT` · `CUSTOM_ROW` | `content` | карточки контента |

Поля карточек — в `src/features/home/types.ts`, это зеркало `HomeFeedDto.java`.

**Карточка контента** отдаёт `durationSeconds` · `episodeCount` · `genre` —
их добавили под экран «Media» (макет заказчика 28.08.2026).

- `durationSeconds` — своя длительность контента, **только у цельного**.
  У сериала «длительности» не существует, она у каждой серии своя; среднее
  было бы выдуманным числом.
- `episodeCount` — сколько **опубликованных** серий, только у многосерийного.
  Черновики не считаются: «12 qism» должно совпадать с тем, что человек
  увидит, открыв контент.
- `genre` — **первый** жанр на языке запроса. На карточке одна строка, а
  жанров бывает несколько; полный список — на странице контента.

Оба числа вместе не приходят: карточка показывает либо таймкод, либо число серий.

**Пустая секция в ответ не попадает** — заголовок без содержимого клиент бы нарисовал
как сломанный ряд.

**Цены в фиде нет.** Карточка отдаёт только `accessPolicy`
(`FREE` · `PREMIUM_ONLY` · `PURCHASE_ONLY` · `PREMIUM_OR_PURCHASE`). Цена приходит
вместе с правом доступа из `/watch`, поэтому на постерах — бейдж политики, а не сумма.

**⚠️ На чистой базе фид пустой.** Ряды главной создаются лениво, при первом обращении
к админскому `GET /api/v1/app/admin/homepage/sections`. Пока админ ни разу не открыл
раздел «Bosh sahifa», `/api/v1/app/home` честно возвращает `"sections": []`, и
приложение показывает пустое состояние. Проверено на локальном бэкенде: 0 секций до
вызова, 12 после.

### `GET /api/v1/app/catalog/categories` · `/catalog/categories/{id}`

Разделы каталога КОНТЕНТА («Drama», «Komediya») — ряды на главной под фидом.

⚠️ Это не 10 направлений кастинга из `src/features/catalog/categories.ts`.
Там анкеты людей на старом API сайта, здесь фильмы и сериалы новой платформы;
id из одного списка в другом не значит ничего.

**Почему отдельный эндпоинт, а не фид.** Секция `CATEGORIES` в `/app/home`
отдаёт только названия, а ряды контента там собраны по ТИПУ (`PODCASTS`,
`SHOWS`, `MINI_SERIES`), не по категории (ТЗ §13 — разные оси). Поля
`categoryId` у карточки нет, то есть ряд «Drama» из фида собрать нечем.

```jsonc
// GET /catalog/categories?locale=UZ  — только названия и счётчики
[ { "id": 3, "slug": "drama", "name": "Drama", "iconMediaId": 12,
    "total": 27, "page": null, "size": null, "hasMore": null, "items": [] } ]

// GET /catalog/categories/3?locale=UZ&page=0&size=10
{ "id": 3, "slug": "drama", "name": "Drama", "iconMediaId": 12,
  "total": 27, "page": 0, "size": 10, "hasMore": true,
  "items": [ /* HomeFeedDto.ContentCard — та же карточка, что в фиде */ ] }
```

- `total` — сколько в разделе ВСЕГО, независимо от страницы. По нему клиент
  решает, показывать ли «Barchasi ›».
- `hasMore` считает сервер, а не клиент: решение «страница последняя» должно
  жить в одном месте.
- `size` по умолчанию 20, потолок 100. Ряд на главной просит 10, экран
  «вся категория» — по 20 на страницу.
- Видно только `PUBLISHED` + `PUBLIC` — то же правило, что у рядов главной
  (`HomeFeedService.isVisible`), поэтому карточка не может быть в фиде и
  пропасть в категории.
- Неактивная категория — `404`. «Есть, но выключена» клиент нарисовал бы
  пустым рядом.

**В приложении.** `src/features/catalog/contentCategories.ts` (список +
запрос на каждый ряд), `CategoryRows.tsx` (ряды на главной: три карточки в
кадре, десять в ряду), `app/category/[id].tsx` (весь раздел страницами по 20,
догрузка при прокрутке).

### `GET /api/v1/app/media/{id}/raw`

Медиа новой платформы. **Другой namespace, чем `/api/v1/file/getFile/{uuid}`**: там
вложения кастинга (UUID), здесь `MediaAsset` (числовой id). Перепутать нельзя —
id из фида в старом эндпоинте даст 404.

Картинки открыты и кэшируются, видео проверяет право доступа и на отказ отдаёт `404`
(не `403` — существование файла тоже не раскрывается). Поддерживается `Range`, то есть
перемотка в плеере работает.

### `GET /api/v1/app/watch/{episodeId}` · `/watch/content/{contentId}`

Право на просмотр: можно ли смотреть, а если нет — `reason` и что делать
(`SIGN_IN` · `SUBSCRIBE` · `BUY_EPISODE` · `BUY_OR_SUBSCRIBE`) плюс цены.
Ссылки на видео в отказе не приходят вовсе. Подключено: экраны
`app/content/[id].tsx` и `app/episode/[id].tsx`.

```
{ "episodeId": null, "contentId": 3, "episodeNumber": null,
  "durationSeconds": 4860, "title": "Meni kechir",
  "orientation": "LANDSCAPE",
  "allowed": false, "reason": "NOT_AUTHENTICATED", "requiredAction": "SIGN_IN",
  "episodePrice": null, "premierePrice": 15000,
  "showAds": false, "sources": [] }
```

Проверено на локальном бэкенде, контент 3 (`PREMIUM_ONLY`):

| Кто спрашивает | allowed | reason | requiredAction | sources |
|---|---|---|---|---|
| гость | false | `NOT_AUTHENTICATED` | `SIGN_IN` | 0 |
| подписка активна | true | `PREMIUM` | `NONE` | 2 |
| подписка истекла | false | `PAYMENT_REQUIRED` | `SUBSCRIBE` | 0 |
| без подписки | false | `PAYMENT_REQUIRED` | `SUBSCRIBE` | 0 |

**⚠️ `/watch/content/{id}` работает только с цельным контентом.** У многосерийного
он отвечает `422 VALIDATION_ERROR`, и это правильный ответ, а не сбой: спрашивать
надо конкретную серию. Приложение по этому ответу переключается на список серий
(см. ниже) — заранее, до запроса, отличить фильм от сериала оно не может.

**⚠️ Тип контента не говорит о структуре.** `contentType` и `structureType` — разные
оси (ТЗ §13, §14): `SHOW` бывает и цельным, и эпизодическим. В карточке фида
`structureType` нет, поэтому заранее, до запроса, отличить фильм от сериала клиент
не может — узнаёт из ответа `/watch`.

**⚠️ Видео требует токен, картинки — нет.** `sources[].url` ведёт на
`/api/v1/app/media/{id}/raw`, а тот проверяет право доступа. Проверено: платное
видео гостю — `404`, подписчику — `200`/`206`; бесплатное — `200` обоим. Поэтому
плееру передаётся заголовок `Authorization` (`authHeaders()` в `src/lib/api.ts`).

**`orientation` — формат кадра, `LANDSCAPE` или `VERTICAL`.** Добавлен в этой
работе: поле было в админке и в карточке фида, но не в ответе `/watch`, и плеер
рисовал рамку 16:9 всегда — вертикальный ролик показывался узкой полоской.

Определить формат по самому файлу нельзя: у закрытого контента `sources` пустой,
а обложку под замком рисовать надо — и у рилса она вертикальная. Поэтому поле
приходит и в отказе тоже.

#### `trailer` — единственное видео, которое отдаётся при отказе

Добавлено 06.09.2026. До этого закрытый экран показывал афишу и замок: посмотреть
до покупки было нечего, хотя главный сценарий ТЗ — «продолжение за 5 000» —
происходит именно здесь.

```
{ "allowed": false, "reason": "PAYMENT_REQUIRED", "sources": [],
  "trailer": { "mediaId": 42, "url": "/api/v1/app/media/42/raw",
               "hlsUrl": "/api/v1/app/media/42/hls/master.m3u8?t=…",
               "durationSeconds": 90 } }
```

- поле той же формы, что элемент `sources`, и открывается тем же `playbackSource()`;
- `null`, если ролик не загружен, — тогда экран прежний, афиша под замком;
- в админке ролик заводится ролью **TRAILER** или **TEASER**; при обоих выбирается
  TRAILER — тизер обычно короче и для анонса, а не для просмотра.

**⚠️ Это не элемент `sources` и не замена ему.** Сам фильм при отказе по-прежнему
не выдаётся. Ролик показывается отдельно и с бейджем «Трейлер»: без подписи
90 секунд в рамке плеера читаются как «фильм уже открыт».

**⚠️ Плееру трейлера передаётся `contentId = null`.** По этому полю пишется позиция
просмотра и считается запуск контента — ни то, ни другое к рекламному ролику не
относится. Иначе «продолжить просмотр» отправляло бы человека на 1:30 фильма,
которого он не покупал, а в отчётах появлялись бы просмотры от тех, кто ничего не
купил. Ломается это тихо, поэтому закрыто тестом
(`__tests__/lockedTrailer.test.tsx`).

**Права:** трейлер отдаётся без entitlement — иначе его видел бы только тот, кто уже
заплатил. Но **только у опубликованного контента**: у черновика поля нет, и сам файл
на `/raw` отвечает `404`, чтобы ролик не утёк до даты выхода. Фильм той же карточки
остаётся закрытым — обе стороны проверяются вместе в `TrailerAccessTest`.

#### Как видео доходит до телефона

В `sources[]` приходят ДВА адреса, и это не дубль:

```
{ "partNumber": 1, "mediaId": 146, "durationSeconds": 164,
  "url":    "/api/v1/app/media/146/raw",
  "hlsUrl": "/api/v1/app/media/146/hls/master.m3u8?t=eyJhbGciOi..." }
```

| Поле | Что это | Когда используется |
|---|---|---|
| `url` | исходный файл через наш сервер | запасной путь, работает всегда |
| `hlsUrl` | плейлист HLS | если транскодирование закончено |

Выбор делает `playbackSource()` в `src/features/watch/Player.tsx` — отдельная
чистая функция, чтобы решение можно было прочитать и проверить тестом.

**⚠️ `hlsUrl` приходит в двух видах, и различает их клиент.** Начинается с `/` —
это плейлист нашего сервера, нужен `BASE_URL`. Начинается с `https://` — это CDN
напрямую, `BASE_URL` добавлять НЕЛЬЗЯ: получилось бы
`https://uzcasting.comhttps://cdn…`, то есть тихая поломка без сообщения. Сервер
не подставляет свой домен сам, потому что за прокси он его не знает наверняка.

На боевом сервере путь всегда первый:

```
телефон → НАШ СЕРВЕР   master.m3u8, 480p/index.m3u8   право проверяется каждый раз
телефон → ХРАНИЛИЩЕ    segment_00001.m4s              подписанная ссылка
```

Гигабайты идут мимо нашего сервера, через него проходят только плейлисты —
несколько килобайт текста.

**Лестница качества — дело плеера, не наше.** Проверено на живом CDN
(`videos/146`): три ступени, H.264 + AAC, fMP4, сегменты по 6 секунд.

```
1080x1920   5.5 Мбит/с
 720x1280   3.2 Мбит/с
 480x852    1.4 Мбит/с
```

AVPlayer и ExoPlayer переключают их сами по фактической скорости сети. Своей
логики замера в приложении нет и не нужно: плеер видит больше.

**Ступень можно зафиксировать, и с 06.09.2026 под кадром есть такой выбор.**
Плеер меряет скорость, а не цену: на хорошем 4G он честно возьмёт 1080p и съест
мобильный трафик там, где человек предпочёл бы 480p.

Переключить дорожку в живом плеере expo-video 57 нельзя — `videoTrack` только на
чтение. Но у каждой ступени есть СВОЙ плейлист, и событие `sourceLoad` приносит
`availableVideoTracks` с готовыми адресами. Выбор ступени = игра её плейлиста
вместо мастера; плеер пересоздаётся, потому что `useVideoPlayer` следит за
строкой источника. Место просмотра не теряется — `useWatchProgress` возвращает
позицию при создании плеера.

**⚠️ Ручной выбор ОТКЛЮЧАЕТ подстройку.** В плейлисте ступени один вариант: при
просадке сети плеер не спустится ниже, а начнёт буферизацию. Поэтому «Авто»
остаётся по умолчанию, а выбор — осознанный размен: предсказуемый трафик вместо
предсказуемой картинки. Правильное решение — урезанный мастер с сервера
(`master.m3u8?max=720`), тогда подстройка сохраняется внутри лимита; это работа
на бэкенде, её пока нет.

**⚠️ Меню появляется, только если ступеней больше одной.** Список приходит от
нативного плеера и может оказаться пустым: не-HLS источник, неподдерживаемые
кодеки, старое устройство. Тогда экран выглядит ровно как раньше. Логика отбора
чистая и покрыта тестами (`__tests__/quality.test.ts`), но САМ список — из
нативного плеера, и в jest его нет: **проверять на стенде**.

**⚠️ `contentType: 'hls'` в источнике обязателен.** Без него iOS не разбирает HLS,
когда после «.m3u8» стоит запрос — а у нас там билет. Ступени пришли бы пустым
списком, и меню молча не появилось бы.

Выбор общий для всех видео (ключ `watch.quality` в хранилище) и наконец
наполняет смыслом поле `quality` в `/api/v1/app/watch-progress`: раньше туда
всегда уходило `auto`, потому что выбирать было нечем.

**⚠️ На путь HLS `Authorization` НЕ отправляется.** Плеер задаёт заголовки на весь
поток, и они попали бы в запрос сегмента — а хранилище отвергает запрос, где есть
и заголовок, и подпись в адресе. Видео не открылось бы вовсе. Право на этом пути
подтверждает билет `?t=` внутри адреса. На старом пути (`url`) заголовок,
наоборот, обязателен.

**⚠️ Адрес живёт ограниченное время.**

| Что | Сколько | Настройка |
|---|---|---|
| билет плейлиста | 6 ч | `app.video.ticket-ttl` |
| подпись сегмента S3 | ~3 ч (4 ч минус окно 1 ч) | `app.video.signed-url-ttl` |
| токен CDN (когда включат) | 4–5 ч | `app.video.cdn.secure-token.secret` |

Фильм, поставленный на паузу вечером и продолженный утром, упирается ровно в это.
Плеер тогда просто замирает чёрным прямоугольником — ни ошибки, ни спиннера.
Поэтому `Player` сообщает о сбое через `onError`, а экран показывает «Видео не
открылось» с кнопкой повтора; повтор перезапрашивает `/watch` и получает свежий
адрес. Место просмотра не теряется: позиция пишется каждые пять секунд, и новый
плеер читает её при создании.

Повтор РУЧНОЙ. Автоматический бился бы в ту же стену: причина бывает и в сети, и
в снятой подписке — во втором случае сервер честно откажет, сколько ни повторяй.

**Что НЕ изменится, когда закроют бакет.** Сейчас хранилище публичное, и подпись
ничего не защищает (проверено 06.09.2026: без подписи приходит `200`). Когда его
переведут в приватный и включат secure token на CDN, поменяется только то, чем
подписан адрес сегмента — а он и так приходит внутри плейлиста, который отдаёт
наш сервер. В приложении менять нечего. Порядок работ — `config/timewebconfig.md`
и `yuklash/yoriqnoma.md` §10.

### `GET /api/v1/app/content/{contentId}/episodes`

Серии контента. Добавлен в этой работе — без него сериалы, мини-сериалы и
подкасты в приложении не открывались вовсе.

```
{ "contentId": 1, "structureType": "SEASONAL", "orientation": "LANDSCAPE",
  "seasons":  [ { "id": 1, "seasonNumber": 1, "title": "Birinchi fasl", "posterMediaId": 31 } ],
  "episodes": [ { "id": 2, "episodeNumber": 2, "seasonId": 1, "seasonNumber": 1,
                  "title": "Sir", "durationSeconds": 1560, "thumbnailMediaId": 36,
                  "accessPolicy": "PREMIUM_OR_PURCHASE",
                  "allowed": false, "reason": "NOT_AUTHENTICATED",
                  "requiredAction": "SIGN_IN", "episodePrice": 3000.00 } ] }
```

- `orientation` относится ко всему контенту, у серии своего формата нет: части
  одного сериала не бывают в разной ориентации.
- `seasons` заполняется только у `SEASONAL`; у `EPISODIC` он пустой — фальшивый
  «сезон 0» не выдумывается, серии просто лежат плоским списком.
- Порядок задаёт сервер: сезон, затем номер серии. Клиент не пересортировывает.
- Неопубликованные серии в список не попадают, неопубликованный контент даёт
  `404` — «есть, но закрыто» само по себе раскрыло бы, что он существует.
- `allowed` / `reason` / `requiredAction` считает тот же `AccessService`, что и
  `/watch`. Проверено на живом сервере: для каждой серии ответ списка совпадает
  с ответом `/watch/{episodeId}`.

**⚠️ Ссылок на видео здесь нет и быть не должно.** Список отвечает «что есть и
что кому открыто»; адрес файла выдаёт только `/watch/{episodeId}` после
подтверждения права. Иначе списка хватало бы, чтобы забрать платную серию.

**Цены приходят отсюда, а не из фида.** В карточке главной есть только
`accessPolicy`, поэтому цену на постере показывать нечем — она известна лишь
после `/watch`.

### `POST /api/v1/app/analytics/events`

Единственный эндпоинт, куда приложение **пишет** (кроме авторизации).

```
{ "deviceKey": "0f1c…",              // случайный UUID приложения, не рекламный ID
  "events": [ { "type": "AD_IMPRESSION", "targetId": 4 },
              { "type": "CONTENT_PLAY", "targetId": 7, "episodeId": 12 } ] }
```

Типы: `AD_IMPRESSION` · `AD_CLICK` · `CONTENT_VIEW` · `CONTENT_PLAY` ·
`CONTENT_COMPLETE` · `NOTIFICATION_OPEN` · `NOTIFICATION_CLICK`.
Ответ — `202`, эндпоинт открыт (показ рекламы надо считать и у гостя).

**Отчёты в админ-панели считаются только из этих событий.** `AnalyticsService`
раз в 5 минут сворачивает их в дневные строки, а страницы «Reklama» и
«Hisobotlar» читают уже готовый агрегат. Пока приложение молчит, показы, клики
и CTR там нули — не «рекламу не смотрят», а «никто не сообщил».

- **Не больше 50 событий в запросе.** Больше — сервер отвергает пачку целиком
  (`MAX_BATCH`), поэтому клиент режет очередь сам.
- **Сервер ничего не дедуплицирует**: сколько прислали, столько и запишет.
  Показ одного баннера отправляется один раз за запуск приложения — иначе
  перерисовка главной набивала бы ему сотни показов и роняла CTR.
- **`deviceKey` не идентифицирует человека.** Он нужен только для «сколько
  разных зрителей»: у гостя нет id, и без ключа все незалогиненные слились бы
  в одного.
- **При `READ_ONLY` отправка выключена целиком** (`ANALYTICS_ENABLED` в
  `src/features/analytics/api.ts`). Приложение по умолчанию смотрит в боевую
  базу сайта, и отладочные показы попали бы в отчёты рекламодателей.

Устройства аккаунта. Требование заказчика — не больше двух на аккаунт —
существовало в базе (`cms_user_device`), в настройке

никогда не сообщало о себе. Регистрация устройства и есть недостающее

### `GET /api/v1/app/tariffs` · `GET /api/v1/app/me/subscription`

```jsonc
// ОТКРЫТ: цена — то, что смотрят ДО входа.
GET /api/v1/app/tariffs?locale=UZ|RU|EN
→ { "locale": "UZ",
    "tariffs": [ { "id": 2, "code": "m3", "durationMonths": 3,
                   "price": 49999, "monthlyPrice": 16666, "currency": "UZS",
                   "highlighted": true, "name": "3 oy",
                   "badge": "ENG FOYDALI TARIF", "description": "…",
                   "features": ["4K sifat", "Reklamasiz"] } ] }

GET /api/v1/app/me/subscription?locale=UZ   // токен обязателен
→ { "active": true, "until": "2026-12-31T00:00:00",
    "history": [ { "id": 9, "tariffCode": "m3", "tariffName": "3 oy",
                   "startAt": "…", "endAt": "…", "source": "PURCHASE",
                   "paidAmount": 49999, "currency": "UZS",

```

- **`features` разбит на строки СЕРВЕРОМ.** В базе это один текст; три

- **`paidAmount: null` — это подарок, а не ноль.** Ноль означал бы
  «купил бесплатно» и попал бы в доход. Так же ведёт себя `PROMO`.
- **`until` сохраняется у истёкшей подписки.** «Закончилась 28.08» и

- **Язык:** `?locale=` → язык профиля → UZ. Значения по умолчанию у
  параметра НЕТ: иначе язык профиля не читался бы никогда.
- **Покупки пока нет** — платёжный провайдер не подключён, кнопка
  «Tanlash» на экране тарифов выключена с честной подписью.

### `POST /api/v1/app/promocodes/redeem` · `GET .../my`

Промокод даёт **бесплатные дни**, и они прибавляются к текущему сроку
(решение заказчика, 04.09.2026). Скидок и процентов нет.

**Что именно даёт — выбирает админ при создании** («для чего создан — к
тому и подключается»):

- `PREMIUM_DAYS` — N дней Premium; он открывает и раздел Casting;
- `CASTING_DAYS` — N дней ТОЛЬКО раздела Casting, фильмы остаются
  закрыты.

⚠️ Тип, как и сам код, при редактировании НЕ меняется: код мог быть уже
разослан, и люди ждут от него того, что обещано.

```jsonc
POST /api/v1/app/promocodes/redeem   { "code": "YANGI-2026" }
→ { "code": "YANGI-2026", "grantType": "PREMIUM_DAYS", "days": 30,
    "until": "2026-10-04T12:00:00" }

GET /api/v1/app/promocodes/my
→ [ { "code": "YANGI-2026", "grantType": "CASTING_DAYS", "days": 7,
      "redeemedAt": "…", "until": "…" } ]
```

Отказы названы по имени — экран показывает свой текст по коду:
`PROMO_NOT_FOUND` · `PROMO_EXPIRED` · `PROMO_ALREADY_USED` ·
`PROMO_EXHAUSTED` · `PROMO_INACTIVE`.

- **Одно общее «код не подошёл» недопустимо.** «Вы уже активировали» и
  «такого кода нет» ведут к разным действиям человека.
- **Две защиты от гонки, обе в базе:** `uk_promocode_user` (один
  человек — один раз) и `select … for update` на строке кода (общий
  лимит). Проверка «сначала посчитать, потом записать» в обоих случаях
  не работала бы.
- **Подбор кодов ограничен** — `RateLimitFilter`, 10 попыток в минуту.
- Выданное пишется в `cms_subscription` с источником `PROMO` и пустой
  суммой — в доход не попадает.

### `PUT /api/v1/app/me`

Имя и язык. Раньше имя записывалось ТОЛЬКО во время входа и потом не
менялось никогда — пункт «Profil» не нажимался, а у вошедших через
Google имя навсегда оставалось гугловским.

```jsonc
PUT /api/v1/app/me   { "name": "Ali Valiyev", "language": "RU" }
→ то же тело, что у GET /api/v1/app/me
→ 422 { "code": "NAME_INVALID" }   // 2–60 символов
```

- **Не переданное поле не трогается.** Смена языка не должна требовать
  повторной отправки имени.
- **Границы имени те же, что на входе** (`PersonName` на бэкенде).
  Разойдись они — имя, принятое в профиле, отвергалось бы при
  следующем входе.
- **⚠️ Язык уезжает сам**, из обработчика в `i18n/storage`: push берёт
  язык из `cms_user_account.language`, а приложение хранило выбор
  только на телефоне. Заметить это можно было бы лишь после включения
  FCM.
- **Аватара здесь нет.** Для загрузки нужен открытый пользователям
  файловый эндпоинт; старый `/api/v1/file/upload` принадлежит
  ЗАМОРОЖЕННОМУ модулю (`OldCastingFrozenTest`), и вешать на него новую
  задачу нельзя. Отдельный шаг.

В ответе `GET /api/v1/app/me` появилось поле `casting`:

```jsonc
"premium": { "active": true,  "until": "2026-12-31T00:00:00" },
"casting": { "active": true,  "until": "2026-12-31T00:00:00" }
```

⚠️ Это НЕ копия премиума. Premium открывает и раздел Casting, но не
наоборот: промокод типа `CASTING_DAYS` открывает только раздел, фильмы
остаются закрыты. `until` — то из двух прав, что заканчивается позже.

### `GET /api/v1/app/notifications`

Уведомления, написанные в админке. Модуль на бэкенде был готов целиком —
таблица, переводы на три языка, расписание, страница в панели, — а
приложение его не читало: экран «Xabarlar» был пустой заглушкой.

```jsonc
GET /api/v1/app/notifications?locale=UZ|RU|EN   // токен обязателен
→ [ { "id": 12, "title": "…", "body": "…", "imageId": 44,
      "sentAt": "2026-09-04T10:00:00",
      "linkType": "INTERNAL", "targetType": "CONTENT", "targetId": 7 } ]
```

- **Только отправленные.** Черновик и запланированное ещё не сообщения:
  первое не дописано, у второго не пришло время.
- **Аудитория учитывается**: `ALL` / `PREMIUM_ONLY` / `NON_PREMIUM` —
  предложение «оформите подписку» не показывается подписчику.
- **Токен обязателен**: без него не ответить на вопрос «кому».
- **`sentAt`, а не `createdAt`**: админ мог написать за неделю до
  отправки, а для человека дата — день, когда он сообщение получил.
- **⚠️ Отметки «прочитано» нет.** Она требует отдельной таблицы и
  записи на каждое открытие; сообщений пока мало. Форма ответа не
  мешает добавить её позже.
- FCM по-прежнему не подключён — push не уходит. Для списка внутри
  приложения это не помеха.

## 6. Чего для мобилки не хватает

- каталог и поиск по контенту, карточка контента (описание, жанры, актёры)
- `structureType` и `orientation` в карточке фида: `orientation` там уже есть,
  `structureType` — нет, и фильм от сериала клиент отличает только по ответу `/watch`
- покупка серии/премьеры и оплата подписки: Click / Payme / Uzum /
  UZCARD / Visa / MC — провайдер не подключён, экран тарифов уже готов
- вывод средств
- объявления о кастинге — **эндпоинта нет ни в старом API, ни в новом**
- чаты (уведомления из админки уже читаются)
- Creator Studio: контент, статистика, 50/50
- пуш-уведомления

Из-за этого `src/lib/placeholder.ts` пока жив — но в нём остались только
объявления о кастинге и цены заказчика. Премьеры оттуда убраны: главная и
вкладка «Premyera» работают на `/api/v1/app/home`, а цены на экране просмотра —
из `/api/v1/app/watch/**`.
